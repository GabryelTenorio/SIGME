# SIGME — auditoria técnica e funcional

Data: 10/09/2026. Base analisada: `main`, commit `78baad5`, com correções locais não commitadas.
Repositório: `/home/e-not-094/projetos/sigme` no Ubuntu/WSL.

## 1. Visão geral

O núcleo de manutenção está funcional nos cenários verificados. Foram corrigidos problemas de autorização, sessões desativadas, integridade transacional, validação e navegação. A execução final passou em **137 testes / 1.021 assertions**, sem falhas. O navegador percorreu **45 combinações perfil/menu**, **17 formulários administrativos** e um fluxo de ocorrência/OS até encerramento e reabertura.

Isso **não significa que todas as combinações possíveis estejam homologadas**, nem certifica segurança de produção, acessibilidade integral ou capacidade sob carga. Há decisões de negócio e verificações operacionais pendentes nas seções 14 e 15. Não atribuí percentual de conclusão da V1 a partir da contagem de testes.

Limites respeitados na implementação: sem push, commit, merge, deploy externo, novas dependências, novas migrations ou restauração do banco principal. Dados de teste são fictícios, em MySQL e armazenamento separados. Não foram usados logins reais nem serviços externos autenticados.

**Incidente operacional durante a preparação:** a primeira chamada ao Compose sem nome explícito colidiu com `COMPOSE_PROJECT_NAME=sigme` de `.env.example` e recriou o container MySQL principal com a configuração de auditoria. O volume original `sigme_mysql_data` não foi apagado. A configuração original foi imediatamente restaurada e os serviços principais foram verificados saudáveis. Não foi aplicado o esquema de testes ao volume original. Não foi realizada comparação linha a linha do banco real. O incidente foi informado durante o trabalho; o novo script fixa `--project-name sigme-audit` para impedir repetição. Mais tarde ocorreu um reinício do ambiente local; somente os containers de auditoria precisaram ser novamente iniciados.

## 2. Arquitetura encontrada

Monólito Laravel 13, PHP 8.5 em Sail, MySQL 8.4, Blade, CSS compartilhado, JavaScript pequeno e Vite 8. Node 24 é o runtime definido no projeto. O login usa sessão Laravel; não há cadastro público nem API pública de negócio separada.

Fluxo principal: `public/index.php → bootstrap/app.php → routes/web.php → middleware de sessão/autenticação/conta ativa → FormRequest + Policy → Controller → Eloquent/MySQL → Blade`.

## 5. Segurança

As correções A01–A05 são as mais importantes. Os testes exercitam negativas de acesso, alteração de IDs, escopo de organização/escola, concessão de perfil e sessão desativada; não dependem apenas de esconder botões.

Controles confirmados em código: senha com cast `hashed`; regeneração de sessão no login; invalidação no logout; limite de cinco falhas por combinação e-mail/IP; mensagens genéricas de credencial inválida; ausência de cadastro público. O limite não equivale a proteção distribuída por IP/rede. Cookies são HttpOnly e SameSite Lax por padrão; `secure` e HTTPS dependem do ambiente e não foram homologados em produção. A configuração padrão de sessão serializa JSON.

Rotas de negócio estão no grupo autenticado. `GET /notificacoes/{id}/abrir` apenas reautoriza e redireciona; leitura é alterada por PATCH. O health check faz uma escrita temporária de sondagem, não uma alteração de negócio.

CSRF foi confirmado em HTTP real no ambiente de auditoria com `APP_ENV=local`: POST de login sem token retornou **419**. Os testes PHPUnit normalmente desativam essa proteção, por isso essa verificação foi separada.

Uploads usam validação de arquivo/MIME, tamanho, nome de armazenamento gerado pelo servidor e autorização sobre a ocorrência/OS. Não há remoção arbitrária por caminho fornecido na requisição. JPEG/PNG/PDF não significa arquivo livre de malware: antivírus, sanitização de PDFs e política de retenção não foram implementados. A OS não possui o mesmo teto de 20 arquivos definido para ocorrência; ampliar limite/quota demanda definição de produto.

A busca de sinks SQL/comando em `app`/`routes` não encontrou concatenação executável de entrada do usuário; o SQL bruto identificado é `select 1` do health check. Consultas de negócio usam Eloquent/bindings. Blade usa escape normal para textos de usuário; nenhum XSS explorável foi demonstrado nesta rodada. Isso não é um pentest de todos os vetores.

Existe **snapshot de banco versionado** em `database/snapshots/sigme.sql.gz`. Seu conteúdo real não foi divulgado nem restaurado nesta auditoria. Backup de banco deve ser tratado como potencialmente sensível mesmo em repositório privado; a presença do arquivo foi confirmada, não a classificação de cada registro. Exclusão/revisão do histórico Git ou rotação de credenciais exige autorização específica.

Não houve consulta a bases externas de vulnerabilidades, scanner autenticado ou leitura de credenciais externas. Portanto, **dependências não estão certificadas livres de CVEs**. Locks e imagens existentes foram preservados.

## 6. UX/UI

A revisão usou as telas reais do ambiente fictício: login, notificações, ocorrência em 390×844, OS em desktop, reabertura e disponibilidade de categorias. As capturas exibidas durante esta conversa foram inspecionadas; não são mocks.

Pontos positivos: linguagem consistente de sidebar, cards e ações; detalhes e ações separados; estado de negócio textual além da cor; mensagens de sucesso claras; labels na maioria dos controles; valores monetários brasileiros. A tela móvel de abertura não apresentou rolagem horizontal global na medição realizada.

A skill de auditoria de interface orientou a distinção entre captura visual, comportamento e acessibilidade. Seu procedimento de contexto salvo externo não foi executado por conflitar com o limite do usuário. A API de captura utilizada retornou imagens na conversa, sem persistência de screenshots no repositório; por isso este relatório não é um pacote visual completo da skill. Nenhuma captura foi publicada externamente.

Pendências visuais concretas: a justificativa de prioridade é obrigatória, mas seu label não exibe o mesmo asterisco dos campos vizinhos; alguns eventos de histórico aparecem como “Ocorrência atualizada”, embora o evento técnico seja mais específico; seleção múltipla de equipe depende de Ctrl no desktop e merece alternativa mais simples. Não foram alteradas regras de prioridade por causa do label.

Sem declaração de conformidade WCAG: não houve teste com leitor de tela, medição completa de contraste, todos os níveis de zoom ou todos os dispositivos.

## 9. Banco

O schema obtido aplicando as 32 migrations existentes somente em bases isoladas contém **32 tabelas, incluindo tabelas de infraestrutura e migrations**, e **48 foreign keys**. Models e migrations estão enumerados no inventário.

Agrupamentos: organizações/escolas/usuários/perfis/permissões e pivôs; ambientes/histórico; categorias/disponibilidade; ocorrências/protocolos/histórico; OS/sequência/equipe/materiais/tempos/custos/histórico; anexos polimórficos; notificações; cache, sessão e fila.

Pontos verificados: unicidade de protocolos/sequências e notificações por evento; relações por escola/organização; decimal para custos; histórico protegido contra alterações normais; restrições de exclusão dos pais dos históricos. A imutabilidade da aplicação não substitui controles de administradores que acessam o banco diretamente. Anexos polimórficos dependem da aplicação para integridade do pai.

Não houve alteração de schema nesta auditoria. Não foi executado `migrate:fresh`, `DROP DATABASE` ou restauração no banco principal. PHPUnit usa exclusivamente `sigme_testing`; navegador usa `sigme_audit_ui`, ambos em container MySQL separado.

Locks foram ordenados ocorrência → OS, e organização → criação de escola/mudança de modo. O teste de modelo obsoleto e os testes de rollback comprovam os cenários descritos; não substituem ensaio de concorrência simultânea sob carga. Hierarquia de ambientes e alterações concorrentes de papéis continuam candidatas a testes de corrida específicos.

## 10. Performance

Otimização realizada: `ServiceOrder::materialTotal/additionalCostTotal` somam relações já carregadas com BigDecimal, sem consultar novamente o banco. O teste verifica resultado exato acima de R$ 10 bilhões agregados e **zero novas queries** durante os totais após eager loading. Quando a relação não está carregada, a soma SQL permanece.

Build final: CSS de aplicação aproximadamente 56,25 kB (11,64 kB gzip), JavaScript 1,07 kB (0,49 kB gzip), além de fontes locais. Não houve inclusão de biblioteca. Vite emitiu aviso não bloqueante sobre o pacote opcional `fontaine`; não foi instalado.

Pendências: filas de ocorrência/OS e vários cadastros usam `get()` sem paginação; verificações de capacidade e seleção de destinatários ainda podem repetir queries conforme número de usuários/escolas; algumas relações são carregadas em excesso. Não há medição de latência em volume real nem teste de carga. Paginar exige manter corretamente escopo, filtros e significado dos totais do painel.

### Reprodução segura

Executar no Ubuntu, em `/home/e-not-094/projetos/sigme`, com as imagens locais já existentes:

```bash
bash scripts/wsl/audit.sh up
bash scripts/wsl/audit.sh test
bash scripts/wsl/audit.sh stop
```

O script não instala dependências nem semeia automaticamente a base UI. Os dados UI desta rodada estão preservados. Em uma instalação nova do ambiente isolado, a base UI precisa ser criada no MySQL **sigme-audit**; aplicar as migrations e executar AuditSeeder somente nesse container, com `APP_ENV=testing`, `DB_DATABASE=sigme_audit_ui` e DB_URL vazio. O seeder recusa outro contexto e não é idempotente para os e-mails fixos; não deve ser executado novamente nesta base já populada. Não usar o seeder no Compose principal.

Não executar `composer setup`, `migrate:fresh`, restauração de snapshot ou `docker compose down -v` para reproduzir esta auditoria. Nunca omitir `--project-name sigme-audit` ao chamar manualmente o Compose isolado. O script evita essa omissão.
